## 1. Research Question & Objectives

In urgent healthcare resource discovery (emergency beds, ICU, ventilators, blood components), availability status changes dynamically at the physical provider facility, but discovery platforms observe these changes only intermittently through scheduled feeds, web scrapers, or manual staff updates.

This study simulates the **Age of Information (AoI)** process under realistic healthcare provider behaviors to answer:
1. How does the age of availability information evolve across diverse provider reporting archetypes (automated, shift-based, bursty, dropped, or delayed)?
2. What are the operational trade-offs of the MedReach platform's existing 30-minute availability window (`CURRENT_AVAILABILITY_MAX_AGE_MS = 30 * 60 * 1000` in `backend/src/services/hospitalDataView.js`) compared to alternative staleness thresholds (10 min, 60 min, 180 min, 360 min)?
3. How do staleness thresholds affect the critical safety error rate (phantom availability: displaying "available" when the physical facility is full) versus information coverage (reverting to "unknown")?

## 2. Theoretical Formulation & System Model (Pre-Registered Choices)

### 2.1 Information-Age (AoI) Formulation
- **Definition**: Let $t \ge 0$ denote continuous simulation time (in minutes).
- Let $k \in \{1, 2, \dots\}$ index successive availability updates generated by a provider.
- Each update $k$ is generated at source timestamp $t_{gen}^{(k)}$ and arrives at the MedReach platform at arrival timestamp:
  $$t_{arr}^{(k)} = t_{gen}^{(k)} + D^{(k)}$$
  where $D^{(k)} \ge 0$ is the total propagation and ingestion delay.
- Only verified updates are admitted into the active observation index. If update $k$ is admitted at $t_{arr}^{(k)}$, the timestamp of the freshest confirmed update available to the platform at query time $t$ is:
  $$U(t) = \max \left\{ t_{gen}^{(k)} \;\middle|\; t_{arr}^{(k)} \le t \land \text{verified}^{(k)} = \text{True} \right\}$$
- **Age of Information (AoI)** $\Delta(t)$:
  $$\Delta(t) = t - U(t)$$
- **Measurement Point Justification**:
  - Primary metric is measured at **query time** ($t_{query}$), representing the moment an incoming user or ambulance search request is evaluated on the backend server (`composeHospitalDataView`).
  - Network delivery and client render add a small downstream latency $\delta_{render} \approx 100\text{--}300\text{ ms}$, which is negligible relative to the multi-minute physical volatility of hospital resources, but we track $\Delta(t)$ in decimal minutes.
- **Initial Condition**: At $t = 0$, an initial confirmed baseline observation is established at $t_{gen}^{(0)} = 0$.

### 2.2 Physical Resource Volatility Model
- Let $X(t) \in \{\text{available}, \text{limited}, \text{unavailable}\}$ represent the ground-truth physical state of the facility resource.
- The state transitions follow a continuous-time jump process with realistic state dwell times:
  - Transition matrix generator $Q$ parameterized by mean dwell times:
    - $\mathbb{E}[\text{dwell}_{\text{available}}] = 45\text{ minutes}$ (high turnover)
    - $\mathbb{E}[\text{dwell}_{\text{limited}}] = 25\text{ minutes}$ (rapidly saturates or recovers)
    - $\mathbb{E}[\text{dwell}_{\text{unavailable}}] = 40\text{ minutes}$ (diversion / bed blocked until discharge)
  - This reflects emergency room and ICU capacity dynamics where capacity surges happen over sub-hour intervals.

### 2.3 Displayed Status & Uncertainty Resolution (MedReach Logic Mirror)
Following MedReach's production contract in `backend/src/services/hospitalDataView.js:31-48`:
- If $\Delta(t) \le \tau_{stale}$ and the latest observation is verified:
  $$\hat{X}(t) = X(U(t))$$
- If $\Delta(t) > \tau_{stale}$ (or if unverified/no data):
  $$\hat{X}(t) = \text{unknown}$$
  *(The system safely withholds the stale observation and outputs `"unknown"` to prevent phantom capacity misdirection).*

### 2.4 Error Classification & Metrics
At each query sample instant $t$:
1. **Accurate Display**: $\hat{X}(t) = X(t)$ (when $\hat{X}(t) \ne \text{unknown}$).
2. **Safe Fallback (Disclosed Ignorance)**: $\hat{X}(t) = \text{unknown}$.
3. **Critical Phantom Availability Error**: $\hat{X}(t) = \text{available}$ while physical state $X(t) = \text{unavailable}$. (Dangerous: sends critical patient to a saturated hospital).
4. **General Status Error Rate**: Fraction of query instants where $\hat{X}(t) \ne \text{unknown}$ and $\hat{X}(t) \ne X(t)$.
5. **Coverage Rate**: Fraction of query instants where $\hat{X}(t) \ne \text{unknown}$.

## 3. Pre-Registered Candidate Staleness Thresholds ($\tau_{stale}$)

We explicitly pre-register 5 candidate thresholds prior to executing simulations:

| Threshold Name | Value ($\tau_{stale}$) | Architectural & Operational Justification |
| :--- | :--- | :--- |
| **Strict Recent ($\tau_1$)** | **10 minutes** | Matches `FRESHNESS_THRESHOLDS_MS.RECENT = 10 * 60 * 1000`. High freshness guarantee; minimal false availability risk, but risks severe coverage loss under manual updates. |
| **Production Anchor ($\tau_2$)** | **30 minutes** | **Production ground truth**: exact threshold used in `backend/src/services/hospitalDataView.js` (`CURRENT_AVAILABILITY_MAX_AGE_MS = 30 * 60 * 1000`). Chosen by MedReach designers to span typical triage and bed cleaning intervals. |
| **Hourly Shift ($\tau_3$)** | **60 minutes** | Matches `FRESHNESS_THRESHOLDS_MS.UPDATED_RECENTLY = 60 * 60 * 1000`. Represents realistic upper limit for high-frequency clinical shift updates. |
| **Loose Directory ($\tau_4$)** | **180 minutes** (3 hours) | Half-shift intermediate threshold typical in state-level public health dashboards (e.g. BMC health, e-RaktKosh periodic crawlers). |
| **Maximum Stale Bound ($\tau_5$)** | **360 minutes** (6 hours) | Matches `FRESHNESS_THRESHOLDS_MS.STALE = 6 * 60 * 60 * 1000`. Beyond this bound, MedReach classifies observations as `OUTDATED`. |

*Rule adherence*: If post-hoc analysis identifies an alternative threshold (e.g., empirical knee point), both pre-registered and post-hoc values will be reported side-by-side.

## 4. Source Update Archetypes & Simulation Scenarios

We pre-register 6 exhaustive scenarios capturing diverse operational environments:

### Scenario 1: Frequent Reliable Updates (Automated / IoT / Telemetry)
- Generation inter-arrival: Gaussian distribution $\mathcal{N}(\mu=8\text{ min}, \sigma=1.5\text{ min})$ bounded $\ge 1\text{ min}$.
- Propagation delay: LogNormal($\mu_{log}=1.5, \sigma_{log}=0.5$, mean $\approx 5\text{ seconds} \approx 0.08\text{ min}$).
- Update drop-out rate: $p_{drop} = 0.01$ (99% reliable network).
- Verification: 100% automated verified ingestion.

### Scenario 2: Infrequent Shift-Based Updates (Manual Ward Logging)
- Generation inter-arrival: Uniform distribution $\mathcal{U}(90\text{ min}, 150\text{ min})$, mean $\mu = 120\text{ min}$ (every 2 hours).
- Propagation delay: Truncated Normal $\mathcal{N}(3\text{ min}, 1\text{ min})$ (manual form submission).
- Update drop-out rate: $p_{drop} = 0.05$.
- Verification: Verified on submission.

### Scenario 3: Irregular & Bursty Updates (Surge-Driven / Event-Driven)
- Inter-arrival: Pareto/Gamma distribution with shape $k=0.7$ (heavy-tailed, bursty), scale $\theta = 42.8\text{ min}$ (mean $\mu = 30\text{ min}$).
- Providers update in rapid succession during surge incidents (3–5 updates within 15 minutes) followed by quiet periods of 2–4 hours.
- Propagation delay: Exponential($\beta = 2\text{ min}$).
- Update drop-out rate: $p_{drop} = 0.08$.

### Scenario 4: High Provider Drop-out / Network Interruption
- Scheduled generation: Nominal periodic schedule $\mu = 20\text{ min}$.
- Drop-out behavior: Two-state Markovian channel (Good vs. Impaired).
  - Normal state: $p_{drop} = 0.10$.
  - Impaired blackout state (staff crisis or connectivity drop): $p_{drop} = 0.85$.
  - Mean duration of impairment: 90 minutes.

### Scenario 5: Delayed Ingestion / Periodic Web Scraper Pipeline
- Generation at source: Frequent updates every $\mu = 15\text{ min}$.
- Ingestion mechanism: Periodic web scraper or batch crawler queue.
- Propagation delay: Uniform $\mathcal{U}(15\text{ min}, 45\text{ min})$ (mean $D = 30\text{ min}$).
- Update drop-out rate: $p_{drop} = 0.04$.

### Scenario 6: Diurnal Shift Handover Cycle
- 24-hour cycle:
  - Peak handover windows (07:00–08:30, 14:00–15:30, 21:00–22:30): Frequent updates ($\mu = 12\text{ min}$).
  - Active day hours: Moderate updates ($\mu = 35\text{ min}$).
  - Night hours (23:00–06:30): Sparse updates ($\mu = 120\text{ min}$).
- Propagation delay: $D \sim \mathcal{U}(1\text{ min}, 4\text{ min})$.
- Drop-out rate: $p_{drop} = 0.06$.

## 5. Statistical Rigor, Replication Plan & Determinism

- **Replication Count**: $R = 50$ independent stochastic replications per scenario.
  - *Justification*: 50 replications over a 72-hour operational window (sampled at 1-minute query intervals, yielding $72 \times 60 = 4,320$ query points per run $\times 50 = 216,000$ query evaluations per scenario) provides narrow confidence intervals (standard error $< 0.2\%$) for rare critical errors (such as phantom availability) while keeping total compute time under 60 seconds.
- **Random Number Generation**: Python `numpy.random.default_rng` initialized with deterministic master seed `20261024`.
- **Metrics Collected**:
  - AoI Distribution: Mean, Std, Median, IQR (p25, p75), P90, P95, P99, Max.
  - Staleness Rate under each $\tau_{stale} \in \{10, 30, 60, 180, 360\}$.
  - Status Mismatch Error Rate (when displayed $\ne$ unknown).
  - Critical Phantom Availability Rate (displayed "available" while physical "unavailable").
  - Time-to-Stale distribution.
